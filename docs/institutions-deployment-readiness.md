# Institutions 2.0 — préparation du déploiement

Cette note décrit la procédure de validation. Les constats propres à la configuration de production sont communiqués au propriétaire hors du dépôt. Aucune base de production n'a été modifiée pendant la préparation.

## Prérequis d'infrastructure

### Préproduction proposée, non provisionnée

Le fichier séparé `render.institutions-staging.yaml` décrit une nouvelle base PostgreSQL 18 à Oregon, sur le même plan de calcul `0.1c-256mb` que la base active, avec 1 Go de stockage, autoscaling désactivé et `ipAllowList: []`. Un service API de préproduction `0.5c-512mb` utilise seulement son URL PostgreSQL **interne**, la branche de #196, `APP_ENV=staging`, aucune clé de fournisseur de production et aucune inscription de compte. L'auto-déploiement est coupé. Ce fichier n'est pas le Blueprint de production `render.yaml` et sa présence dans Git ne crée aucune ressource.

Au tarif catalogue Render vérifié le 11 novembre 2026, la base minimale coûte **6 $ US/mois** (1 Go inclus) et le service API Starter **7 $ US/mois**, soit **13 $ US/mois** de ressources supplémentaires si elles restent actives un mois complet, hors taxes et éventuels dépassements de bande passante/build. La restauration PITR vers une **seconde** instance PostgreSQL ferait monter le tarif simultané à **19 $ US/mois** tant qu'elle existe ; la durée effective détermine le montant au prorata. Aucun coût n'est engagé avant approbation. L'offre PostgreSQL Free ne convient pas à ce protocole : pas de sauvegardes, limite de 1 Go et expiration à 30 jours. Le service web Free ne donne pas de Shell ni de one-off job pour piloter et mesurer l'import. Sources : [tarifs](https://render.com/pricing), [offre gratuite](https://render.com/docs/free), [sauvegardes](https://render.com/docs/postgresql-backups).

Le bundle SEC T2 2026 pèse 25,6 Mo compressé et 140,7 Mo décompressé. La taille finale PostgreSQL, index compris, **n'a pas été mesurée** ; 1 Go est le point de départ le moins cher, pas une garantie de capacité. Si l'espace libre devient insuffisant, interrompre l'essai et soumettre le coût d'un passage à 5 Go avant d'augmenter le stockage. Render ne permet pas de le réduire ensuite.

Le service de préproduction est construit depuis la racine du dépôt pour rendre les wrappers `scripts/` disponibles dans son Shell. Le service de production utilise `rootDir: apps/api` : il doit appeler les commandes embarquées `python -m app.ops.institutions ...`, sans supposer que les scripts du dépôt existent dans son conteneur. Le Blueprint séparé ne doit être relié à Render qu'après accord explicite sur les deux ressources et leur tarif.

- Vérifier sur Render que l'API utilise une URL PostgreSQL **persistante**, que le producteur de données et l'API pointent vers la même base, et que la région, la version et le plan de calcul sont adaptés. Ne jamais afficher la valeur de `ACCOUNT_DATABASE_URL` dans les journaux, les tickets ou les PR.
- Vérifier la capacité libre, la limite de connexions, l'autoscaling, le pool et les métriques de calcul. La [grille Render](https://render.com/docs/compute-plans) et la [documentation des connexions](https://render.com/docs/postgresql-creating-connecting) précisent les limites du plan choisi.
- Vérifier la fenêtre PITR et créer **puis restaurer en essai** un export logique avant toute migration. Voir la [documentation Render sur les sauvegardes](https://render.com/docs/postgresql-backups).
- Inventorier les clients externes de PostgreSQL et fermer ou restreindre l'accès externe ; les services Render dans la même région peuvent utiliser le [réseau privé](https://render.com/docs/private-network). Toute modification de sécurité en production requiert l'autorisation du propriétaire.
- `render.yaml` ne provisionne ni PostgreSQL ni tâche planifiée ; `ACCOUNT_DATABASE_URL` y est une variable `sync: false`. La présence d'une variable dans le Blueprint ne prouve pas sa valeur ni sa correspondance avec une ressource PostgreSQL donnée.

## Compatibilité du schéma

`scripts/migrate_institutions.py up` appelle `InstitutionStore.create_schema()`. Les sept tables et leurs index sont définis dans un `MetaData` séparé : `institution_snapshots`, `institution_details`, `institution_holdings`, `institution_filings`, `institution_ingestion_runs`, `institution_symbol_map` et `institution_ingestion_leases`. Le script n'appelle aucune migration des tables `account_*`. Un test local exécute réellement la CLI `up` deux fois sur une base contenant une ligne `account_users`, puis vérifie que la ligne et le schéma du compte sont identiques. Ce test SQLite vérifie la portée du code, **pas** les verrous, permissions ou performances PostgreSQL.

Sur le head de #196, le démarrage de l'API ne crée plus les tables Institutions et ne lance plus l'import du bundle ni la découverte SEC par défaut. Les variables `INSTITUTIONS_STARTUP_INITIALIZATION_ENABLED` et `INSTITUTIONS_BACKGROUND_DISCOVERY_ENABLED` demandent un opt-in explicite. Les comptes existants continuent leur démarrage habituel. La migration et l'import Institutions se font séparément, sous contrôle, après sauvegarde. Cette protection n'arrive toutefois qu'avec #196 : les déploiements automatiques de `main` doivent être suspendus avant d'intégrer #194 et rester suspendus jusqu'à ce que la pile complète soit fusionnée et validée. Pendant l'import initial, les détails peuvent répondre 503 ; le classement garde le snapshot embarqué.

## Essai obligatoire sur une préproduction isolée

Préparer une base PostgreSQL 18 distincte, avec comptes synthétiques ou copie anonymisée, même taille de calcul si possible, et une application de préproduction pointant **uniquement** vers elle. Vérifier son identité par un canal administrateur sans copier de chaîne de connexion dans un journal, une PR ou un ticket. Ne pas utiliser la base de production ni la base suspendue sans nouvelle autorisation.

1. Arrêter les collectes de préproduction. Relever le schéma, les nombres de lignes des tables `account_*`, l'espace libre, le nombre de connexions et les métriques CPU/RAM. Vérifier l'absence de collisions avec les sept noms `institution_*`.
2. Créer un export logique complet depuis Recovery et vérifier qu'il est récupérable. Après approbation distincte du coût de la seconde instance, restaurer le point de reprise sur une nouvelle base Render isolée et vérifier le compte synthétique. La restauration ne doit jamais viser la base active. Le PITR Render exige un point vieux d'au moins dix minutes. Ne pas placer l'URL ou un mot de passe PostgreSQL dans une ligne de commande ou dans les sorties.
3. Depuis le commit final de #196, avec `ACCOUNT_DATABASE_URL` injecté par `fromDatabase` dans le service de préproduction, exécuter `python scripts/migrate_institutions.py up` via le Shell de ce seul service. Vérifier les sept tables, index, droits SQL et l'absence de changement du schéma et des lignes `account_*`. Répéter `up` pour vérifier l'idempotence. L'équivalent disponible dans le service de production est `python -m app.ops.institutions migrate-up --expected-database <nom_vérifié> --allow-production`, à n'utiliser qu'après approbation de l'opération. Un schéma Institutions volontairement incompatible sur **une copie jetable de préproduction** doit être détecté par la vérification, puis restauré ; ne jamais créer ce défaut dans la base active.
4. Relever le nom réel de la base de préproduction dans Render (Render peut suffixer le nom demandé), puis exécuter depuis son Shell `python scripts/import_institution_bundle.py import --expected-database <nom_réel_préproduction>` ; le script refuse une autre base, vérifie la période, les 100 gestionnaires, les **395 419** positions et les index avant de publier le résultat. Relever durée, CPU/RAM, connexions et taille des tables. Exiger une période publiée `2026-06-30`, rechercher un CUSIP présent et vérifier ses dépôts SEC. Redémarrer l'API, puis exécuter `python scripts/import_institution_bundle.py verify --expected-database <nom_réel_préproduction>` et confirmer que la période, les comptes et les positions persistent sans nouvel import.
5. Appeler le classement, `/{cik}`, `/security/activity`, `/security/holdings`, `/periods`, `/history/{cik}`, `/security/history?q=<CUSIP>`, et `/api/v1/admin/institutions/quality` avec une session administrateur de test. Vérifier 401 sans session et 403 pour un non-administrateur. Contrôler les pages web ordinateur/mobile, leurs graphiques historiques et l'état à un seul trimestre sans point inventé.
6. Mesurer p50/p95 de chaque endpoint à chaud et à froid, avec plusieurs requêtes concurrentes, et relever le CPU/RAM de l'API et du PostgreSQL, le pic de connexions, la taille des tables/index, la durée de l'import et les erreurs/attentes de verrous. Comparer au comportement initial et conserver les résultats anonymisés. Les chiffres SQLite locaux ne satisfont pas ce jalon.

Pour tester le retour arrière, le PITR de préproduction doit créer une **nouvelle** instance, jamais réécrire la base de départ. Une restauration logique de données synthétiques dans une autre base de la même instance peut aussi vérifier l'export, si les outils PostgreSQL 18 et l'espace libre sont disponibles. Les deux essais doivent contrôler le schéma et le compte synthétique après restauration. Une restauration de la base de production n'est pas prévue dans cet essai.

## Architecture de collecte

| Option | Connexion | Effet opérationnel |
| --- | --- | --- |
| GitHub Actions actuel (`.github/workflows/institutions-13f-sync.yml`) | URL PostgreSQL externe et secret GitHub `INSTITUTIONS_DATABASE_URL` | Le job est quotidien sur `main` et saute la collecte si le secret manque. Les adresses des runners hébergés changent ; [GitHub déconseille de s'appuyer sur leurs plages IP](https://docs.github.com/en/enterprise-cloud@latest/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses). Cette option demanderait une exposition externe contrôlée, le chiffrement TLS et une gestion de la liste d'accès. |
| Tâche planifiée Render | URL interne de la même base, dans la même région et le même espace Render | Le trafic reste sur le réseau privé et Render garantit une seule exécution simultanée de la tâche. C'est l'option recommandée après essai de la taille mémoire et du temps de collecte. [Render facture la tâche selon sa durée avec un minimum de 1 $ US par mois](https://render.com/docs/cronjobs) ; ne pas la créer sans accord sur le coût. |

La tâche Render doit utiliser `python scripts/sync_institution_store.py --if-new`, conserver le `SEC_USER_AGENT`, recevoir une variable secrète vers l'URL **interne** et disposer d'assez de RAM pour reconstruire le trimestre. Après validation de son premier cycle, retirer la planification GitHub ou conserver le workflow sans secret pour éviter deux collecteurs. Aucun changement de scheduler n'est effectué à ce stade.

Avant de restreindre l'accès externe de PostgreSQL, vérifier la destination réelle de chaque service Render qui possède une variable de connexion, les éventuelles applications hors Render, les sessions d'administration et la présence du secret du workflow GitHub. Une simple présence de `ACCOUNT_DATABASE_URL` ne prouve pas que le service pointe vers cette instance. Tester les consommateurs internes avec l'URL privée, puis seulement retirer la règle publique pendant une fenêtre approuvée, avec contrôles de santé et plan de retour arrière. Ne pas publier les URL ni les secrets dans ce rapport.

## Retour arrière et ordre de fusion

- Avant la fusion, figer un commit de chaque PR et revalider les quatre jobs `api-tests`, `web-build`, `mobile-quality`, `e2e` sur ce commit. Fusionner, uniquement avec l'accord du propriétaire, dans l'ordre #193 → #194 → #195 → #196. Les bases des PR sont empilées dans cet ordre ; réactualiser chaque branche après la fusion de sa base et attendre à nouveau les contrôles.
- `main` alimente normalement un déploiement automatique Render et le site web a son propre déploiement. Avant **la première fusion**, suspendre ces déploiements avec l'accord des propriétaires des plateformes, ou préparer une retenue vérifiée ; #194 ne doit pas être déployée seule. Après les quatre fusions autorisées, déployer l'API d'abord avec les deux drapeaux Institutions désactivés, créer une sauvegarde restaurable, exécuter migration puis import via la procédure approuvée, vérifier les comptes et les lectures, puis seulement déployer l'interface web. N'activer la découverte SEC que si la collecte planifiée et ses droits sont validés.
- En cas d'échec applicatif, revenir au dernier déploiement sain et laisser les tables Institutions additives en place ; elles ne modifient pas les comptes. Ne **jamais** lancer `migrate_institutions.py down` en production. Réserver une restauration PITR ou logique à une corruption confirmée et coordonnée : restaurer toute la base peut aussi faire perdre des écritures récentes des comptes.
- Aucun test réel de migration, import, persistance, p50/p95 ou consommation sur PostgreSQL de préproduction n'a encore été exécuté : aucun accès à une base active isolée n'est disponible. Aucun coût nouveau n'a été engagé.
